## Run procedure

The 60-minute cable-attached session on the same phone, running each engine once, with both recorded via Instruments (`xcrun xctrace`):

1. **Setup (dev panel):** set `CaptionEngineChoice` to the engine to run; start phone on screen, unlock, plug into Xcode host
2. **Baseline capture:** record start battery %, room temperature, note in manifest
3. **xctrace start:** launch the Energy Log + Core ML trace capture via `scripts/battery-run/record.sh <device-udid> <output-name>`
   - Sets Idle Stop to Never in Settings before starting (so the session runs the full 60 min)
   - Records timestamp, then manually picks the engine in the dev panel and starts captioning
   - Verifies receiver is at 1m, plays speaker audio through the speaker (not earpiece)
4. **Run 60 min:** app stays foreground, speech plays continuously (or: record gaps when it stops, factor into later analysis)
5. **xctrace export:** on completion, the script exports the XML and optional CSV for analysis
6. **Baseline record:** note end battery %, confirm thermal state never hit `.critical`

**Manifest template:** `scripts/battery-run/manifest.example.json` — one row per run, named `manifest-<date-engine>.json`.

The script (step 3) automates the Energy Log capture and export; steps 1, 2, 4 and 6 are manual. See the script's help for the exact steps.

## Candidate fixes and the latency trade-off

**Hypothesis (pending the component split to confirm which is the biggest cost):**

The three levers to reduce Neural Engine load are listed in order of caption-latency risk (lower latency cost first):

1. **Widen diarizer drain cadence** (latency cost: ~+10-20 ms speaker-relabel response)
   - Today: Sortformer runs on every 16 kHz buffer (20 ms cadence)
   - Option: run every Nth buffer (e.g., 40 ms, 60 ms) to cut its frame count in half or by 2/3
   - Impact: same diarizer accuracy if N is small; relabel latency rises as N grows
   - Already measured: `AdaptiveHop` in the engine switch design is the speech model's lever; this would be Sortformer's

2. **Loosen silence gate or lower floor of adaptive hop** (latency cost: ~+0.1-0.2 s initial detection)
   - Today: skip Parakeet decodes when RMS is below room-noise baseline (quiet = no work)
   - Option: require RMS > baseline *and* uncomitted span > threshold (e.g., 0.5 s instead of 0.0 s) to start decoding
   - Impact: room-noise resilience unchanged; speech detection may lag slightly in very quiet rooms
   - Already in design: adaptive hop's current floor (0.5 s) is tuned by check C4; lowering it reduces the latency tax for going slower

3. **Reduce caption redraw rate on the volatile tail** (latency cost: ~0 if targeted well)
   - Today: every decode emits the volatile tail (uncommitted words after the last final)
   - Option: skip emitting if the tail hasn't changed since the last decode, or batch updates every Nth hop (e.g., 2 decodes)
   - Impact: volatile tail updates become blockier, less "alive", no accuracy change
   - Not yet measured: would need a UI redraw profile to know its actual Neural Engine share

**Confirmation order:**
- If component split shows diarizer > 40% of Neural Engine time: focus on option 1
- If Parakeet encoder+decoder > 40%: focus on option 2
- If neither is dominant: likely spread across three, so test option 3 (redraw batching) in the next run

**To confirm which option is worth the latency trade-off:** re-run the lab session with the leading candidate fix applied, measure both battery *and* latency (the ADR 0015 benchmark), and compare.

## Notes

- The measurement is one session on one phone model (iPhone 17, 128 GB). To show generalization, a second iPhone 16 or 16 Pro run is later (AC6 or later ticket); the Instruments lab procedure stays the same.
- Thermal state logged here is `ProcessInfo.thermalState` as seen by the app on the main thread (app's perspective), not the system's internal thermal budget or system-wide Neural Engine throttle state.
- The app's `battery.maxThermalState` field in beta reports (schema, ADR 0023) is the same `ProcessInfo` value, so the compare should be close if the run was steady.
- If the session hits `.critical`, the fallback to Apple's engine fires mid-session, so the later part of the trace will show only Sortformer (diarizer) and Apple's engine, not Parakeet. Check the trace's timestamps and the app's log for the switch point.
