# Whole-system replay: design (#273)

Every accuracy number before #273 scores **engines alone**: `engine-eval` hands whole clip files to a
`FileTranscriber` on the Mac (#145, #150). The app never does that. It streams the microphone in small buffers
through converters, a speaker model, a sound labeler, a fallback policy and its own line building. A regression
anywhere between the mic and the screen passes every test we had. The owner reports 1.1.0 (10) was very inaccurate
in a live demo, while the App Store 1.0 (Apple's engine) on another iPhone was accurate in the same setting
(owner, 2026-11-09, on #273). This harness replays the same recordings through each build's own live path and
scores what she would have read.

## The path it drives

```
recording (48 kHz Float32, the iPhone mic's shape)
  -> AudioSource                        ReplayAudioSource: 4096-frame buffers, each handed over when its last
  |                                     sample has been "spoken" (deadline pacing, ReplaySchedule; tested)
  -> TranscriptionEngine                the build's own: converters, 16 kHz side path, diarizer, sound labeler,
  |                                     loudness, EngineFallbackPolicy triggers, the recognizer CaptionEnginePlan picks
  -> CaptionSessionController           start, listening, Stop, cleanup: the app's own controller
  -> CaptionStream.apply                CaptionModel.onUpdate's own call: the lines she reads
  -> SessionLog (JSON)                  plan + reason, every engine seen, every FallbackReason, every update with
                                        wall and audio times, the final lines
```

Two ways in, because 1.0 has no `AudioSource` (its mic is wired into the engine):

- **source**: `ReplayAudioSource` into `TranscriptionEngine.start()`, exactly as the microphone (1.1.0 (9) on).
- **replaying**: the engine's own `startReplaying(fileURL:)`, in every build since 1.0: the same converters,
  recognizer, diarizer and lag clock, fed from the file in 4096-frame buffers at real-time pace. The 1.0 vs 10
  comparison uses this path for both builds, so neither gets a different mechanism. The session ends with a Stop tap
  2 s after the recording has played (1.0's replay never ends its stream on its own; build 10's does at the file's end).

Arm D checks the mechanism itself: build 10 through the source path vs through replaying.

Not on the Mac: the iPhone audio session (category, mode, Bluetooth and route, `MicSessionSetup`), Live Translation
in the ear and voice match (#233, #247), real memory pressure (`os_proc_available_memory` is iOS only; physical
memory stands in, as in the simulator), thermal state, the fallback history (empty per session, so one replay never
pins the next). These need the device run below.

`scripts/system-replay/at-build.sh REF NAME` checks a build out as a detached worktree, copies this harness in,
pins FluidAudio to **that build's** `Package.resolved`, and builds in release (as the app ships). Every build here
resolved FluidAudio 0.17.5.

**Pinning matters.** CaptionCore declares `FluidAudio from: "0.17.5"`. A root package that doesn't pin resolves the
newest 0.x: this harness first resolved 0.18.3 (released 2026-11-07) and would have replayed speech and speaker code
no build shipped. The app's Xcode project is generated by xcodegen and its `Package.resolved` is not committed, so an
archive made after a clean resolve would do the same. Evidence that builds 9 and 10 did not: every CaptionSpike
DerivedData on the laptop, including one last resolved 2026-11-04 11:04 (five minutes before the build 10 commit),
holds 0.17.5. That rules drift out for build 10 as far as the evidence goes, but nothing stops it next time.

## Data

EdAcc (#145's corpus, CC BY-SA 4.0), shard 1 (accent-stratified, already on the 2012 Mac mini). Conversations:
each EdAcc segment id is `<split>-<conversation>-<n>`. For each conversation, its shard-1 segments in segment order
are joined into one recording, 1.0 s of silence between, 3.0 s after (the quiet before she taps Stop). Two people,
real turns, minutes long: a session, not a clip. Segments #145 doesn't score (empty after normalisation) are left out.

- **Scored: the test split** (40 conversations, 37.0 minutes).
- **Development: the validation split** (36 conversations, 40.9 minutes). Every check of the harness itself ran here.
- Gap, tail, buffer size (4096), rate (48 kHz) and the Stop moment were fixed before any test-split run and never
  tuned on scored clips.

Limits of stitching: digital-zero silence between turns (a room is never that quiet), and turn gaps that are
uniform where real ones vary. Real-room recordings (restaurant, car, TV on) remove both; they need the owner's
consent for anyone recorded.

## Scores

- **WER** = (S + D + I) / N, #145's normaliser and alignment (`scripts/engine-eval/edacc_eval`), pooled over
  conversations. Hypothesis = the text of the CaptionStream lines (what she reads), sound labels left out.
- **95% CI**: percentile bootstrap, 1,000 resamples, resampling **conversations** (each holds its two speakers, so
  correlated segments stay together). **Paired differences** resample each conversation's pair of arms together.
  A difference whose CI excludes 0 is real at this sample size.
- **Engine-only gap**: the #145 engine-only hypotheses for the same clips (`ultra-pal6` and Apple
  `SpeechTranscriber en-US`, repeat 1), joined per conversation and scored by the same rule. Whole system minus engine
  only = the app's own loss.
- **Lag**: the engine's own word lag (`WordLagTracker`, ADR 0015) for every arm; finished-line lag (wall time a final
  line arrives minus its audio end) on the source path only, whose clock zero is the first buffer. The replaying path
  hands each buffer over at its start, about one buffer (85 ms) earlier than a mic would; that is the same for every
  replaying arm, so their lags compare with each other, not with the source path's.

Speaker labels (DER, split rate) are logged per update (`speaker`, audio times) but not scored yet.

## Running it

```sh
# once per build
scripts/system-replay/at-build.sh 4e7f55a build-1.0-5
scripts/system-replay/at-build.sh be128a5 build-1.1.0-10
# conversations (needs shard 1 from the 2012 mini)
python3 -I scripts/system-replay/replay.py stitch --shard ~/seal-replay/edacc/shard-001 --out ~/seal-replay/convs/test --split test --48k
# arms A-D, real time (about 2.5 hours for 37 minutes x 4)
scripts/system-replay/run-ab.sh ~/seal-replay/convs/test test ~/seal-replay/ab-test
# score
python3 -I scripts/system-replay/replay.py score --conversations ~/seal-replay/convs/test/conversations-test.jsonl \
  --arm "A 1.0 Apple=~/seal-replay/ab-test/A-1.0-apple" --arm "B 10 Parakeet=..." ... \
  --engine-only ~/seal-replay/edacc/apple-shard-001.jsonl --out results.json --markdown results.md
```

Tests: `swift test --package-path Packages/SystemReplay` (pacing, session log) and
`python -m pytest scripts/system-replay` (stitching, scoring, paired bootstrap).

## What the device run needs

The owner's report is about an iPhone, so the Mac result can only narrow it down. On a device:

1. **A debug build of 1.1.0 (10) and of 1.0 (5)** from the commits above, each with the harness's session logging
   (plan, engines seen, every `FallbackReason`, every update). The app has a debug-only `FileAudioSource` (#220);
   it sleeps a fixed 100 ms after each buffer, so it runs slower than real time and inflates the lag clock. The device
   run should use `ReplayAudioSource`'s deadline pacing instead (move `ReplaySchedule` into CaptionCore).
2. **The same audio played to both phones**, and for an acoustic test, through a speaker in the same room, recorded
   by each phone's own mic. A file into the engine shows the software; a speaker into the mic adds the mic, its
   processing and the audio session.
3. **Build 10's real audio session**: Live Translation on and off; the ear (#233) on and off, with and without
   headphones (it switches to `.playAndRecord` with A2DP and prefers the built-in mic); voice match (#247) on and off.
4. **Real `os_proc_available_memory` and thermal state** logged at plan time and through the session.
5. **Settings to record on each phone**: caption language and region; which models are on the device
   (`SpeechModelInstaller`, the bundled Parakeet); 1.0's vocabulary list (contextual strings, dropped later), which
   only 1.0 used.
6. **Confounders to record**: phone model and mic, iOS version, room noise level, distance to each speaker.

## Hypothesis checked: did setup-first downloads leave sessions silently on Apple's engine?

Asked before the owner's correction. Reported as a hypothesis with evidence, not a conclusion. **The owner's
correction rules it out as the explanation for the demo**: 1.0 is Apple's engine, and it was accurate, so a session
that had silently fallen back to Apple's engine would have looked like 1.0, not worse.

What the code says, 1.1.0 (9) `3c56e56` to 1.1.0 (10) `be128a5`:

- **Setup-first downloads (#245) only fetch Apple's speech models and translation packs.** Parakeet Ultra is a
  required bundled resource in both builds (`project.yml`: xcodegen fails without it), so `modelMissing` can't come
  from a download. One-way captions keep `.downloadIfNeeded`; only the split uses `.mustBeOnDevice`.
- **`EngineFallbackPolicy.engine` changed order**: the language check now runs before the model check, and
  Parakeet's languages grew from English to en, es, fr, de, it, pt. For English nothing changes.
- **Ways a 1.1 session can still be on Apple's engine without saying so** (all already in build 9): the warm engine
  (EngineWarmupHost) is planned at launch or after a pause, and `take()` checks only mic mode and language, so a
  `lowMemory` or `repeatedFallbacks` verdict at warm time carries into the session; two fallbacks in 24 h
  (`noWordsFromSpeech`: 20 s of loud audio with no words; `memoryWarning`; `loadFailed`) pin every session to
  Apple for a day; nothing on screen says which engine runs. Build 10 adds more memory users (Live Translation in the
  ear, voice match, the into-language speech download in Settings), not measured.
- The beta report carries `engine` and `engineFallback`, so the owner's session data answers this directly.
