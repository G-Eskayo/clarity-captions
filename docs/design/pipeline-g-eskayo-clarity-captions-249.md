## North-star fit

**Reuses:** the `scripts/engine-eval` package-per-domain pattern (`edacc_eval`, `translation_eval`, `speaker_eval`, each with its own `cli.py` subcommand, a `report.py` that writes a markdown doc plus an optional `--json-out` twin, and a `tests/` module per file — see `edacc_eval/cli.py:48-58`, `edacc_eval/report.py:399-432`, `tests/test_report_languages.py`). I add a sibling package, `scoreboard_eval`, rather than inventing a new convention. The row-level engine identifiers already exist in `Packages/CaptionCore/Sources/CaptionCore/EngineFallbackPolicy.swift` (`SealModel`, `CaptionEngineRouting.parakeetLanguages`) — the scoreboard's "engine" column names match these where the language is already routed, so a future step 2 can read the scoreboard without a vocabulary mismatch.

**Why this is the simplest sufficient approach:** the raw per-clip measurements never land in this repo (they live on the M4 Mini/2012 mini, e.g. `~/ami-eval/results`, `~/edacc-eval/results-203`) — only the finished comparison docs under `docs/perf/` are committed. So "generated from the measurements we already have" (the ticket's own words) has to mean: read the committed `docs/perf/*.md`/`*.json` files, not re-score anything. Two of them (`translation-languages-results.json`, `speaker-scoreboard-*.json`) already have a structured JSON twin and need no scraping; the rest (`engine-accuracy-comparison.md`, `language-accuracy-comparison.md`, `hebrew-accuracy-comparison.md`, `hebrew-coreml-comparison.md`, `ear-translation-spike.md` + its `ear-translation/*.json`) only exist as markdown/raw-measurement JSON, so I write one small, explicitly-tested extractor per file rather than a generic table scraper — a generic scraper is exactly the kind of fragile machinery that's easy to get subtly wrong (which is my best guess at why the last two attempts failed code review with no visible trace of why).

**Where it saves/spends tokens:** spends a modest, bounded amount now (one new small Python package, no iOS/Swift involved at all) to save a lot later — this is the one place step 2's routing, step 3's gap list, and step 4's Android column will all read from, so every later ticket in #249's chain gets cheaper.

**Phone-OS direction:** indirect — this is a build-time quality gate, not something the phone touches. It matters because it's what keeps "always the best engine" honest as the device/language matrix grows, which is a precondition for MARVIN/Seal being reliable anywhere.

**More capable or more passive:** this is pure tooling for the owner/maintainer, not a user feature; it doesn't touch the end user. Gil stays the one deciding what ships — the scoreboard reports, step 2 (later) routes, and ADR 0025/0026-style owner sign-off still gates what the device actually runs.

**Crucially, this touches zero Swift/Xcode files.** No `CaptionCore`, no `Apps/Spike`, no `Apps/Mac`. Checked against `.github/workflows/ci.yml`: the `caption-core`, `spike-app` and `mac-app` jobs all gate on a path-based `--affected` check, and nothing under `scripts/engine-eval/` or `docs/perf/` is in those paths, so this PR triggers none of them — it carries none of the iOS-Simulator-build risk that parked this ticket in October. Verify is `cd scripts/engine-eval && python3 -m pytest` (not part of the CI merge gate today, same as `edacc_eval`/`translation_eval`/`speaker_eval`'s own tests), plus a manual read of the generated `docs/perf/engine-scoreboard.md` for sanity. **Untested by me:** nothing — there is no UI, app, or device behavior involved in this round's scope, so there's nothing the pipeline's simulator screenshot step applies to either.

## Tests first

No "How we'll try to break it" section exists on this issue, so these come from the north star's adversarial-testing principle plus concrete landmines found while reading the actual source files:

1. **Missing known source file** (e.g. `hebrew-coreml-comparison.md` not yet on disk, or `#271`/`#272` not landed) → that source is skipped, logged under a `gaps` list, generator still succeeds and writes the other rows.
2. **Malformed/corrupt JSON twin** (e.g. truncated `translation-languages-results.json`) → raises a clear, file-naming error rather than silently dropping or guessing rows (missing ≠ malformed: the first is expected and common, the second means the format drifted and must not be swallowed).
3. **CI-interval format drift across sources** — three different real shapes exist today: `"13.8% | 12.7% – 14.7%"` (engine-accuracy), `"56.2 to 57.4"` with no `%` (translation-languages-results.md's "All languages Apple supports" table), and `"ci95": [lo, hi]` floats (speaker-scoreboard JSON). A parser keyed to only one shape must be caught failing on the other two.
4. **Unit drift for size** — `speaker-scoreboard.md` itself mixes `"229.4 MiB"` and `"92.6 MB"` in two different tables of the *same file*; `translation-languages-results.json` gives raw `disk_bytes`. Test that `MiB → bytes` and `MB → bytes` convert to different, correct byte counts (they differ by ~4.86%), and the rendered column is consistently one unit.
5. **Empty table** (a source file present but its table has a header row only, e.g. a not-yet-run language) → zero rows contributed, no crash, no spurious gap entry (it's "present but empty," not "missing").
6. **Huge input** — `engine-accuracy-comparison.md`'s "by accent" table has ~29 rows and multiple sub-tables; feed a synthetic 200-row fixture and confirm linear-time parsing with no truncation.
7. **Duplicate measurement of the same (language, engine, platform, test set) key inside one file** (e.g. a corrupted table with a repeated row) → raises rather than silently keeping the first or last.
8. **The same engine measured on two different test sets** (Apple `es` scores differently on FLEURS vs. the "all languages" FLORES run) → both rows survive with distinct `test_set` labels; nothing is silently discarded as a "duplicate."
9. **Unknown file dropped into `docs/perf/`** that isn't on the extractor allowlist (a person's mistake, or a stray file) → ignored entirely, not picked up by an accidental glob.
10. **Stale state / idempotency** — running the generator twice back to back on unchanged sources produces byte-identical output; running it again after one source file's number changes updates only that row, not a cached stale one.
11. **Output path not writable** (parent dir missing, or `docs/perf` read-only) → a clear error, not a partial/half-written file.
12. **"Not run" placeholder rows** (e.g. `#203`'s `ultra-pal3`/`ultra-pal2`/`ultra-mixed246`, explicitly "not built") → surfaced as rows with `metric: not measured`, not omitted and not coerced into a fake number.
