## North-star fit

- **Reuses before adding anything new:** `BetaFeedback.swift`'s `ConversationRecorder`/`ConversationReport.battery` (`dropPercentPer30Min`, `maxThermalState`) already measures real on-device battery drop and thermal state per conversation, split by `engine` (ADR 0023/0025) — this is the primary number this ticket needs, already shipping in 1.1.0. The developer panel's `CaptionEngineChoice` picker (`ContentView.swift:1746`, `CaptionEngineFactory.swift`) already lets a session run Parakeet or Apple. `IdleStop`'s "Never" preset (ADR 0019) already lets a session run unattended for 60 minutes with the screen awake. `docs/perf/caption-latency-baseline.md` already sets the repo's precedent for leaving a real-hardware number as **"pending"** rather than fabricated, when the agent doing the work has no phone. `docs/research/evidence-log.md`'s per-file format (`scripts/check-evidence.mjs`) is reused as-is for the new entry.
- **Why this is the simplest sufficient approach:** no app code changes are needed to produce the numbers — engine switching, idle-stop, and battery/thermal measurement are all already shipped. The only genuinely new things are (a) the Mac-side Instruments/`xctrace` capture+parse tooling to get the *component split* (screen/mic/Parakeet/Sortformer/sound-labels) that `BetaFeedback` doesn't break out, and (b) the write-up/comparison/evidence docs.
- **Where it saves or spends tokens/effort:** spends a little now on reusable capture/parse scripts; saves on every future battery/heat check (this is the second time this exact measurement is needed — see ADR 0025 §7 C4 — and it will recur for every future engine or cadence change).
- **Does it leave the user more capable:** yes for the primary user (her phone will last the dinner); this slice itself is measurement/tooling, not a behavior change, so N/A for "more capable vs. passive."
- **Correcting the ticket's own stated fit:** none needed — the ticket's "Purpose" and "North star 3" framing matches the code as it stands.

### The blocker this plan must surface plainly

Acceptance criteria 1–3 require **real elapsed-wall-clock battery and heat data from two physical iPhones, running Instruments/`xctrace` over a cable, with a human playing real speech from a real speaker for 60 real minutes**, exactly as the ticket's own "Blocked by" line and ADR 0025 §7 (C4) already say: *"Needs a real iPhone of each kind, so it runs on a Mac with the phones attached."* This headless worktree has no attached iPhones, cannot run Instruments, cannot play audio at a microphone, and cannot wait out 60 real minutes against real hardware state. No amount of code changes in `Packages/CaptionCore` or `Apps/Spike` substitutes for that — simulated/replayed audio (the existing `whole-system-replay` harness) measures accuracy, not real battery drain, because nothing pads real wall-clock time or draws real current.

This is very likely why the two prior automated attempts failed review after 3 iterations each ("must-fix issues") — the acceptance criteria as written cannot be satisfied by writing code alone. My recommended scope: **build everything that makes the real run turnkey and its results mechanical to write up**, and leave the actual data-collection step explicitly marked as Gil's (or whoever has physical access to both phones) to run interactively — not something this pipeline should keep retrying automatically to "pass."

## Tests to write first (per "How we'll try to break it" + misuse)

All of these are on the new parsing/tooling code, since that's the only code this ticket can add; there is no new Swift/app logic to put under `swift test`.

1. **Trace-parser rejects a run left on the charger or in Low Power Mode** — given a parsed battery/LPM sample showing `charging: true` or `lowPowerModeSeen: true` at any point, the script flags the run invalid and refuses to emit a row into `battery-<date>.md`'s table, per "Phone left on the charger... is thrown out, not averaged in."
2. **Trace-parser separates out a `.serious`/`.critical` thermal excursion** — given input where `maxThermalState` reaches `.serious` partway through, the output explicitly reports it as a separate annotated line (not folded into the averaged number), per "recorded and reported separately."
3. **Start-charge / room-temperature mismatch between the two engines' runs is caught** — given two run manifests (one per engine) with different recorded start-charge % or temperature, the script errors out rather than silently comparing them.
4. **Screen-off/locked run is rejected** — given a trace or beta report whose `minutes` of active capture is materially shorter than the wall-clock duration of the window (screen dimmed/locked), the run is flagged invalid, not included.
5. **Beta-report vs. Instruments disagreement beyond a few points is flagged, not silently trusted** — given a parsed Instruments-derived %/hour and a `ConversationReport.battery.dropPercentPer30Min` (×2) for the same session, if they differ by more than the stated few-point threshold, the comparison script prints which one looks wrong (e.g., checks whether the beta figure's underlying `batteryMinutes` was long enough to be reliable, `>= 0.5` per `ConversationRecorder.entry`) rather than averaging or picking one.
6. **Malformed/empty/huge input to the parsers** — an empty `.trace` export, a beta-feedback JSON that fails `docs/beta/metrics-schema.md`'s schema (schema version ≠ 1, missing `battery` object), and an absurdly large exported CSV (memory/streaming behavior) are all handled without a crash and with a clear error, not a fabricated zero.
7. **Repeats / wrong order** — re-running the parser twice on the same trace file is idempotent (no duplicate rows); feeding the Apple-engine trace where the Parakeet-engine trace was expected (manifest/engine mismatch) is caught, not silently mislabeled.
8. **A person's mistake: wrong device or wrong build** — the manifest requires device model and app build to be recorded alongside each trace/report; a mismatch between the manifest's claimed device/build and what the parsed trace or beta report itself says (e.g. `device.model`, `app.build`) is rejected.
9. **Evidence-entry format** — `node scripts/check-evidence.mjs` passes on the new entry file once real numbers exist (structural check only: the five required fields and the `YYYY-MM-DD-<slug>.md` filename pattern); a test asserts the entry template, with its fields filled, satisfies `problems()` returning `[]`.

Nothing here needs a mock of `BetaFeedback`'s rules — the parser consumes the real `ConversationReport` JSON shape straight from `docs/beta/metrics-schema.md`, which is the real collaborator's contract, not a stand-in for it.

## Task List

1. **`scripts/battery-run/` tooling (new, pure/parsing, tested per the list above):**
   - `parse-trace.mjs` (or similar): takes an `xctrace export`'d XML/CSV from an Instruments Energy Log capture and emits a JSON component split (screen, mic, Parakeet/ASR, Sortformer/diarizer, sound-label process share) plus the run's thermal/charging/LPM flags.
   - `parse-beta-report.mjs`: takes a `seal-feedback-*.json` (per `docs/beta/metrics-schema.md`) and extracts, per conversation, `battery.dropPercentPer30Min` × 2, `battery.maxThermalState`, `engine`, `device.model`, `build`.
   - `compare.mjs`: given a trace-derived row and a beta-report row for the same session, checks the few-point agreement rule and the validity rules (tests 1–8), and prints a flagged/clean verdict.
2. **`xcrun xctrace` capture helper** (`scripts/battery-run/record.sh`): a thin wrapper that records a fixed-duration Energy Log/Core ML trace against a named device UDID and writes the export CSV, so Gil only runs one command per (phone, engine) pair instead of driving Instruments.app by hand. Documents the manual steps it doesn't automate (picking the engine in the dev panel, setting Idle Stop to Never, starting captioning, playing the speaker audio, noting start/end battery % and room temperature in the run manifest).
3. **Run manifest template** (`scripts/battery-run/manifest.example.json`): device model, build, engine, start charge %, room temperature, screen state — the fields tests 3/8 validate against.
4. **`docs/perf/battery-2026-11-14.md`**: the write-up template — run procedure, the four-row result table (phone × engine) left as `TBD`/`pending` per cell, a section for "biggest single cost" with the candidate-fix hypothesis below stated as *to be confirmed by the component split*, and the beta-report-vs-Instruments comparison section, structured the same way `caption-latency-baseline.md` already does for a pending real-hardware number.
5. **Candidate-fix analysis (can be done now, no hardware needed):** write up, from the existing design (ADR 0025 §7 "Risks", `AdaptiveHop`, `LiveDiarizer`'s every-buffer drain), 1–3 candidate fixes with their caption-speed cost against the ADR 0015 10% budget — e.g. (a) widen the diarizer's drain cadence instead of every buffer, trading speaker-relabel latency for less Neural Engine work; (b) lower `AdaptiveHop`'s floor less aggressively / tighten the silence gate's threshold; (c) reduce caption redraw rate on the volatile tail. Mark this section as a hypothesis ranking, pending the real component split to confirm which is actually biggest.
6. **Evidence entry** (`docs/research/evidence/2026-11-14-battery-per-hour-1-1-0.md`): drafted with the required five fields but **not filled with real numbers until the real run exists** — left as a stub that intentionally will not pass `check-evidence.mjs` until Decision d141-scope resolves and real data lands, so nothing fabricated is checked in.
