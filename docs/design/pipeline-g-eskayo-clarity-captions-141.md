## North-star fit

- **Reuses:** the C4 check already fully specified in `docs/design/parakeet-engine-switch.md` §7 (60 min table session, speaker at 1 m, screen on, 80-90% start charge, same room temperature, once per engine) — this ticket just extends C4 to an SE-class phone and compares it against `BetaFeedback.swift`'s `ConversationRecorder.batteryDrop`/`maxThermal` fields (already captured per-conversation, ADR 0023) and `docs/beta/metrics-schema.md`'s `battery.dropPercentPer30Min`/`maxThermalState`. Nothing new to design. The write-up format reuses `docs/perf/caption-latency-baseline.md`'s pattern exactly: a measurement table with **TBD** placeholders plus "how to fill in," and an explicit **Status** line — never a fabricated number standing in for a real one, matching how `docs/perf/speaker-scoreboard.md` / its evidence entry (`2026-11-09-sortformer-fp16-real-voice-baseline.md`) only ever cites a number that was actually run.
- **Simplest sufficient approach:** don't invent new tooling (no app code changes — nothing in `CaptionCore` needs to change to take this measurement; `ParakeetBackend`, `AdaptiveHop`, and the beta-report fields already exist and need no instrumentation added). The only sufficient new artifact is the write-up doc + evidence entry, prepared now with the protocol locked and placeholders ready, so the hands-on run is the only remaining step.
- **Where it spends/saves tokens:** spends nothing on code; saves the owner from re-deriving the protocol (it's copied verbatim from §7, extended) when he sits down with the two phones.
- **Capable vs. passive:** this plan does not pretend to produce a real answer to "what's the biggest battery cost" — doing that from imagined numbers would be worse than not doing it, since the evidence log and the portfolio/marketing site draw from it (`docs/research/evidence-log.md`). Leaves the owner more capable by having the protocol, the template, and the comparison method ready to execute, not by inventing a result for him to unknowingly rely on.

**This ticket cannot be completed by this headless session.** Every acceptance criterion needs a real measured number from a real 60-minute session on a physical iPhone SE (3rd gen) and a physical iPhone 17 Pro, played speech from a real speaker, read off Instruments/`xctrace` while attached to a Mac — hardware this git-worktree session has no access to. §7's C4 row is the same conclusion the project already reached: this check runs "on Gil's iPhone 17," not in CI or an agent sandbox. Writing placeholder numbers into `docs/perf/battery-<date>.md` or the evidence file would violate "verified, not assumed" and would plant a false number somewhere the portfolio/marketing site could later cite. So what follows is split: prep work this session can actually do now, and the hands-on run that needs the owner (or whoever has both phones) at a Mac.

## Tests first

None — there is no `CaptionCore` or app code change in this ticket's scope, so there's no red/green XCTest to write. The only "test" that applies is the evidence checker, which is mechanical and run after the real doc exists:
- `node scripts/check-evidence.mjs` must pass on the new evidence file (five required fields, correct filename pattern `YYYY-MM-DD-<slug>.md`, first line `# Title`).
