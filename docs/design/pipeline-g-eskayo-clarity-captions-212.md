## North-star fit

**Reuses:** `CallArrival` (`Packages/CaptionCore/Sources/CaptionCore/CallArrival.swift`) is the existing pure state machine for one call arriving over the room; its `handle(_:captioning:)` pattern, `Effect` list, and the `CallFlow.perform(_:)` queueing of effects (`Apps/Mac/Sources/CallFlow.swift:53-134`) are reused directly — this ticket generalizes that single level into a stack of the same kind of frame, it doesn't replace it. `CallWatcher`/`CallSignal` (`CallWatcher.swift`) stay the only detection source — no new permission, no new source of truth. `CallNotifier` (`Apps/Mac/Sources/CallNotifier.swift`) is reused for the one notification channel the owner picked, instead of adding a second notification path. The existing `pausedRoom` tuple in `CallFlow` (stream/names/session) is generalized into a stack of the same tuple shape rather than inventing a new persistence model. `SessionRetention.shouldSave` / `SavedConversation.from` are reused unchanged for every save offer at every depth, including stacked ones.

**Why simplest sufficient:** the single-call model already gets 9 of the table's 17 event columns right today (ringing-while-idle, decline, ended-before-answered/missed, double-signal repeats, captions-off path) — confirmed by reading `CallArrivalTests.swift`. The actual bug the ticket names ("the owner's bug") is concretely visible in `CallArrival.handle`: `(.call, .callStarted)` isn't a matched case, so it falls through to `default: return []` — a second call ringing during a captioned call is silently swallowed as a repeat signal today. Fixing that one gap, plus generalizing the single `resumeRoomAfter: Bool` into a small stack of paused frames, covers the "calls that stack" section without a parallel second mechanism.

**Where it saves/spends:** spends the tokens/engineering budget on the pure-logic layer (cheap, fully unit-testable, no simulator needed) and on documenting one place (`docs/mac-calls-behavior.md`) that both the tests and the real-call checklist point at, so the owner's real-call pass (an acceptance criterion only *he* can run) checks against written rows instead of re-deriving behavior by hand each time.

**Phone-OS direction:** reliability under multiple concurrent events (notifications, overlapping triggers) is exactly the kind of "nothing breaks silently" discipline the phone-OS north star needs — this hardens a pattern (paused/resumable context, stacked) that will recur anywhere MARVIN itself has to juggle more than one interrupting event.

**Capable vs. passive:** it protects the primary user's transcripts and makes multi-call handling predictable, which is squarely "protects an irreplaceable record" rather than automating away a choice she'd want to make (every save/caption choice still asks her).

**One north star pushes back:** minimise-resources (north star 1) argues against inventing a general `CallStack` abstraction if only 2 levels are ever realistic — but the acceptance criteria explicitly require a **three-deep** stack test, so the generalization is spec'd, not speculative.

## Design: generalizing `CallArrival` into a stack

- **New/changed type in `CaptionCore`:** generalize `CallArrival`'s single `resumeRoomAfter: Bool` into `private var paused: [Frame]` where `Frame` is `.room(captioning: Bool)` or `.heldCall(app: String)`. Pushing a frame = "hold and accept"; the top of `paused` plus the current `step`/`callApp` is the whole picture. `banner`, `Step`, and existing `Effect` cases stay; new cases are additive, not replacements, so every existing test in `CallArrivalTests.swift` keeps passing unchanged (regression safety).
- **New events:** `secondCallStarted(app:)`, `secondCallEnded` (that ring stopped on its own before any answer), `holdAndAccept` (FaceTime "Hold & Accept": push current call as `.heldCall`, start the new one), `endAndAccept` (FaceTime "End & Accept": end the current call, remember the next app as a pending takeover, resolve to `.startCall(app)` once its save prompt is answered instead of resuming/restoring), `callHeld` / `callResumedFromHold` (the plain Hold control on a single active call — same room-pause mechanics, generalized to apply to a call frame too).
- **New effects:** `.holdCall` (keep the current call's stream/session aside, like `.pauseRoom` does for the room), `.announceSecondCall(app:)` (Notification-Center-only; never an in-window banner — the owner's "announce" decision), `.resumeHeldCall` (pop a `.heldCall` frame and resume it, generalizing `.resumeRoom`).
- **`CallFlow` (Mac app layer):** generalize `pausedRoom: (stream, names, session)?` into `private var paused: [(stream: CaptionStream, names: SpeakerNames, session: ConversationSession, frame: CallArrival.Frame)]`, mirroring the pure model's stack 1:1 so `perform(_:)` stays a straightforward switch with no new control flow shape.
- **Notification policy:** `CallFlow.send` currently gates the OS notification on `!CallNotifier.windowInFront` (`CallFlow.swift:59`). Per the owner's "announce: Notification Center only" decision, drop that gate — every ringing/second-call announcement always goes through `CallNotifier`, never the in-window `CallBannerView(kind: .ringing)`. This is a look change (removing an existing banner state), but the owner's decision checkbox in this ticket (association: owner) is the written approval the pr-requirements/look-change gate asks for, and it's a removal of a state, not a new visual to mock up, so no new mock-up is produced; this is called out explicitly in the PR rather than assumed silently. `CallBannerView(kind: .ended)` (the save-transcript prompt) is unaffected — it's not a "call announcement," it's the post-call decision, and nothing in the Decisions changes where it shows.
- **Detection layer caveat (flagged, not guessed silently):** translating "a second call rang," "Hold & Accept," "End & Accept" into those new events from raw Core Audio process activity is new and, unlike the original single-call signal (verified against a real recorded FaceTime call, evidence E24), has no recorded real second-call/hand-off timeline to replay — FaceTime's `[out]` flag is already shown present throughout an active call in the one real timeline we have, so it can't by itself distinguish "second call ringing" from "call continuing." The plan is to build the detection heuristic in `CallWatcher`/`CallSignal` as best-effort (documented assumptions in code comments) and cover it with **pretend** signal-sequence tests (same style as `RealFaceTimeCallReplayTests` but explicitly labeled pretend, not real), while the PR states plainly that second-call/hold/hand-off detection on a real Mac is untested by this agent — exactly what acceptance criterion 3 already asks the owner to verify by hand with screen recordings.
- **Scope guard (Seal-lane note on the issue):** nothing here touches PR #231/`#213`'s translation work; if the stack design turns out to need a change there, that goes on #213, not into this PR.
