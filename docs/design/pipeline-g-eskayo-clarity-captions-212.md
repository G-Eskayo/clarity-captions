## North-star fit

**Reuses:** `CallArrival` (`Packages/CaptionCore/Sources/CaptionCore/CallArrival.swift`) is the existing pure state machine for a call arriving over the room — its `handle(_:captioning:)` shape and `Effect` list are generalized, not replaced. `CallFlow.perform(_:)` (`Apps/Mac/Sources/CallFlow.swift:89-120`) keeps its "await effects in order" queueing. `CallWatcher`/`CallSignal` stay the only detection source (no new permission). `CallNotifier` stays the one notification channel. `SessionRetention.shouldSave`/`SavedConversation.from` are reused unchanged for every save offer, at every stack depth.

**Why simplest sufficient:** the single-call model already gets most of the table right (ringing-while-idle, decline, missed, double-signal repeats, captions-off path — confirmed by reading `CallArrivalTests.swift`). The one gap the ticket names ("the owner's bug") is concrete: `CallArrival.handle` has no case for `(.call, .callStarted)` or any second-call event, so it falls to `default: return []` — a call arriving while another is captioned is silently swallowed today. Generalizing the single `resumeRoomAfter: Bool` into a small stack of paused frames (room or held call) covers the stacking rules without a second parallel mechanism.

**Where it spends tokens:** on the pure-logic layer (cheap, fully unit-testable, no simulator) and one behavior-table doc that both the tests and the owner's real-call checklist point at.

**Phone-OS fit:** "nothing breaks silently" under overlapping interrupting events is exactly the discipline MARVIN itself will need when juggling more than one interrupting signal.

**Capable vs. passive:** protects transcripts and makes multi-call handling predictable; every save/caption choice still asks her, nothing is auto-decided except what the owner's Decisions already specify.

**1. A design smell that should be removed, not fixed-in-place.** The prior `CallArrival`'s `.ended` handler had an `if paused.isEmpty` branch that silently guesses `.restoreRoom` with a comment "Default; caller may override" — dead, ambiguous code, since every path into `.call` pushes exactly one frame first, so `paused` is never actually empty when `.ended` is reached. My version keeps that invariant explicit (documented, not defended with a guessing fallback) instead of carrying speculative dead code into review again.

**2. A real detection gap, not just an implementation bug.** The prior attempt's `secondCallStarted` detection compares the *live app's name* before and after (`CallFlow.swift`'s `watcher.onChange`). That only catches a **different app** taking over (FaceTime active, Zoom rings) — it is structurally blind to the owner's actual reported bug, a **second FaceTime call** while a FaceTime call is live, because `CallSignal` groups FaceTime, Continuity and its call services all under one name ("FaceTime"), so the name never changes. The only real recorded evidence we have (`docs/research/evidence/E24-...md`, replayed as `RealFaceTimeCallReplayTests`) is a single, one-call timeline — there is no recorded Core Audio timeline for two overlapping FaceTime calls, so whether a second incoming call even produces a *distinguishable* Core Audio signal (e.g. a second `AudioObjectID` reporting input) is unverified, not just untested. I'll improve the heuristic to compare the **set of recording `AudioObjectID`s** CallWatcher already tracks (not just the resolved app name) — if an additional object starts reporting input while the app name stays the same, treat that as a second call too. This strictly dominates the prior same-name-only check (catches everything it caught, plus the same-app case *if* macOS actually exposes a second object for it). I'll cover it with a synthetic/pretend test, explicitly labeled pretend. But I'll state plainly, in the plan and PR, that whether a real second FaceTime call produces a second `AudioObjectID` at all is **unverified and may not be true** — if the owner's real-call pass (acceptance criterion 3) shows no second object appears, this detection cannot be fixed by this ticket at all (CallKit's call observer is unavailable on macOS per `CallWatcher`'s own doc comment, so there may be no programmatic signal available), and that would need a new technical decision, not a code fix. ## Design: generalizing `CallArrival` into a stack (reusing the prior attempt's shape, with its 9 bugs fixed and the smell in point 1 removed)

- `Frame`: `.room(captioning: Bool)` / `.heldCall(app: String)`; `private var paused: [Frame]` replaces `resumeRoomAfter: Bool`. Invariant: entering `.call` always pushes exactly one frame first, so `.ended`'s pop is never applied to an empty stack — no defensive fallback needed.
- New events: `secondCallStarted(app:)`, `secondCallEnded`, `holdAndAccept(heldApp:)`, `endAndAccept`, `callHeld`, `callResumedFromHold`.
- New effects: `.holdCall`, `.announceSecondCall(app:)`, `.resumeHeldCall`.
- `endAndAccept` records the pending incoming app and pushes it correctly (prior bug #2 fixed); `callHeld` always pushes a frame (prior bug #3 fixed).
- `CallFlow`: generalize `pausedRoom` into `pausedFrames: [(stream, names, session, frame, startedAt)]`; fix the `onChange` guard so `secondCallStarted` can actually fire (prior bug #1); pass the *held* app, not the incoming app, to `holdAndAccept` (prior bug #4); restore `callStartedAt` on resume (prior bug #5); drop the `!CallNotifier.windowInFront` gate per the "announce" decision, with **no** new in-window banner reintroduced for ringing/second-call (prior bug #6 — this time, removed and kept removed, since it's the approved look change).
- `CallWatcher`/`CallSignal`: detect a second call via a growing set of recording `AudioObjectID`s (not just app-name change), as in point 2 above; keep this explicitly labeled best-effort/unverified in code comments.
- `CallNotifier`: a second notification category/identifier (`seal.call.second`) with "Hold & Accept"/"End & Accept"/"Not now" actions, independent `requestID` so both can be live at once.
