**This is very likely why the last two automated attempts failed the pipeline's screenshot comparison** (`unchanged`, then `regressed`): "unchanged" is consistent with an attempt that touched `TranslatedCaptionLook`/`DemoMode` defaults but missed that the live iPhone/iPad paths bypass `TranslatedCaptionView` entirely via hard-coded `else` branches, so the real screen never changed. "regressed" is consistent with an attempt that *did* switch `ContentView.swift` over to `TranslatedCaptionView` but dropped the `said`-text's press-and-hold word selection (#107): the hand-written "today" block wires `.textRenderer(renderer)` and `.trackWords(in: textFrames, key: "text-\(line.id)")` onto the said-text so `HoldLocationGesture`/`textFrames.captionLine(at:)` can find it; `TranslatedCaptionView.saidText` is currently a bare `Text` with neither modifier. Swapping it in as-is on the iPhone would silently break line selection/Copy on every translated line — exactly the kind of regression the pipeline's comparison is positioned to catch, and exactly the kind of thing that must be fixed by design, not retried blindly a third time.

## Fix for the regression risk

Give `TranslatedCaptionView` a way for a caller to supply its own said-text view instead of always using the plain default, so the iPhone can keep #107's selection wiring:

```swift
/// The said line's own view. Defaults to plain muted text; a caller that needs selection or hit-testing on it
/// (ContentView's #107 press-and-hold) supplies its own.
var saidView: ((String) -> AnyView)? = nil
```
`folded`'s body calls `saidView?(said) ?? AnyView(defaultSaidText)` instead of the current private `saidText`. `ContentView.swift` passes `saidView: { AnyView(Text($0).font(.body).foregroundStyle(mutedColor(style)).textRenderer(renderer).trackWords(in: textFrames, key: "text-\(line.id)")) }`; `FaceToFaceView`/`CallPopupView` call sites omit it (their old "today" branches never had selection either — no regression there).
