## North-star fit

**Reuses:** `LiveDiarizer` + `SpeakerPathReplay` (`Packages/CaptionCore/Sources/CaptionCore/LiveDiarizer.swift`, `SpeakerPathReplay.swift`) and the `engine-eval speakers` CLI / `speaker_eval` Python package / `m4-speakers.sh` driver built for #271's Sortformer-build scoreboard, plus the opt-in synthetic-voice harness from #58/ADR 0017 (`SpeakerModelComparisonTests.swift`, `SpeakerModelComparisonReport.swift`). Nothing here is a new comparison pipeline — it's the existing one generalized from "one model, many compressed builds" to "many models."

**Simplest sufficient approach:** `SortformerDiarizer` and `LSEENDDiarizer` both conform to FluidAudio's `Diarizer` protocol (same `DiarizerTimelineUpdate` shape), so `LiveDiarizer`/`SpeakerPathReplay` only need generalizing from "hardcoded `SortformerDiarizer`" to "any `Diarizer`" to run LS-EEND through the *exact* same scored path Sortformer already uses. `Nemotron3Diarizer` and `OfflineDiarizerManager` (the ticket's "embedding-and-clustering diarizer... not capped at four") do **not** share that protocol — adapting them into the full AMI/CHiME-6 scoreboard isn't worth the lift for a first measurement, so they get small adapters in the lighter synthetic-voice harness only.

**Tokens:** spends tokens now on pure Swift, no network, matching ADR 0007/0014/0017's "no network in the default suite" rule — `swift test` stays free. Defers the expensive part (downloading non-bundled models, running real corpora) to hardware this sandbox doesn't have.

**Phone-OS direction:** neutral — this is Mac call-captioning quality (#172), not phone-OS work.

**Capability:** a 5+ person Zoom/Teams call stops silently merging voices into 4 slots — strictly capability-raising for the deaf primary user and anyone captioning a bigger meeting.

**Machine:** Mac Mini (issue's own `claimed:mac-mini` label), because the real measurement step needs the M4 Mini's existing AMI/CHiME-6 corpora and `scripts/engine-eval/m4-speakers.sh` — not this worktree.

**Critical finding that reshapes scope:** every real-voice corpus already licensed into this pipeline caps at ≤4 speakers (AMI: 4, one meeting 3; CHiME-6: 4; AliMeeting: 2–4) — confirmed in `docs/research/evidence/2026-11-09-speaker-test-corpora-and-their-licences.md`. VoxConverse (which does have 5+ speaker recordings) was already rejected there for Sortformer scoring on two independent grounds: ambiguous "research purposes" wording next to a paid-app's commercial use, and Sortformer training-set overlap. **No corpus in this repo's pipeline can validate >4-speaker accuracy on real voices.** The only >4-speaker evidence buildable this session is the ticket's own synthetic `say`-voice harness; real validation needs either a new, cleared corpus or the owner's own 5+ person recording (already gated as optional in the issue). ADR 0017 must say this plainly rather than imply the existing AMI/CHiME-6 scoreboard answers the question.

**Model-cap facts** (read from `FluidAudio`'s checked-out sources, pinned revision `0b1f46289`): Sortformer `numSpeakers = 4` (hardcoded). `Nemotron3Diarizer` `numSpeakers = 8` (hardcoded, streaming, own non-`Diarizer` shape). `LSEENDDiarizer` speaker cap comes from the downloaded model's metadata (`maxSpeakers`, variant-dependent — `.ami` is the "up to 10" variant the issue names). `OfflineDiarizerManager` (VBx embedding+clustering) has no fixed slot count at all but is **batch-only** (`process(audio:) async throws -> DiarizationResult`) — it cannot produce a live "time to first label," so even a DER win can't make it the Mac's live diarizer under ADR 0015's latency budget. This is a design fact, not an open question — I'll record it, not ask about it.

**No Decisions block needed:** the issue's one Decision (`model-delivery`) is already answered by the owner. Whether to switch models can't be decided until real measurements exist, and this sandboxed session has no network access to download LS-EEND/Nemotron3/Offline models (none are bundled; `scripts/fetch-diarizer-models.sh` only fetches Sortformer) and no physical device for memory/CPU/battery profiling — the same blocker ADR 0017 hit originally. I will not fabricate numbers; the harness and tests are built and left ready for a run on networked, real hardware.

## Tests (written first)

No "How we'll try to break it" section exists on this issue, so these are derived from the standard misuse checklist applied to the harness code being added:

1. **Regression:** Sortformer through the new generic `LiveDiarizer`/`SpeakerPathReplay` path produces byte-identical segments/emissions to today's concrete path, on the existing fixture — the generalization must change nothing for the shipped model.
2. **Missing dependency:** model missing at `modelURL` still throws `SpeakerModelError.modelMissing` through the new generic path (unchanged).
3. **Dependency failure:** a diarizer factory that throws during `prepare()`/load (e.g. no network for LS-EEND) surfaces the error from `SpeakerPathReplay.run` instead of hanging or crashing.
4. **Empty input:** `next()` returns `nil` immediately → zero segments/emissions, no crash.
5. **Malformed input:** overlapping/out-of-order phrases still throw `SpeakerReplayError.phrasesNotAStream` before touching the diarizer, on the new multi-candidate path too.
6. **Under-capacity misuse:** feeding 10-voice audio through a 4-slot model (Sortformer) doesn't crash; asserts `speakersFound <= 4` and correspondingly higher DER — this *is* the bug the ticket exists to document.
7. **Over-capacity:** feeding 6-voice audio through a 10-slot model (LS-EEND ami) doesn't invent extra speakers; `speakersFound` stays near ground truth.
8. **Determinism:** repeat runs of the same candidate on the same audio are compared (mirrors #275's existing tie-break bug); the new aggregation code must not introduce a *new* nondeterminism source (e.g. dictionary iteration when building the report list).
9. **Person's mistake:** two results with an identical `modelName` string in one comparison run don't silently merge or crash the report/markdown rendering.
10. **Stale/huge input:** phrases whose end time extends past the actual audio length don't index out of bounds.
11. **Per-candidate isolation:** one voice's `/usr/bin/say` failure (bad voice name) fails only that candidate (`SPEAKER-COMPARE-ERROR`), not the whole test — already true today; extend coverage to the new voice-count and new-model cases.
12. **Global state / "wrong order":** each candidate explicitly sets `ModelHub.offlineMode` to the value *it* needs before running, rather than inheriting whatever the previous candidate in the same process left behind (today's comment only covers Sortformer→LS-EEND ordering; Nemotron3/Offline add more candidates that must not depend on run order).
13. **Malformed numeric output:** a candidate that produces `NaN`/`infinite` DER (e.g. empty hypothesis vs. non-empty reference) formats safely in `summaryLine()`/markdown — this is the exact bug class ADR 0017 already had to fix once (`%s` with a Swift `String` crashing XCTest); new fields (peak memory, speed) must not reintroduce it.
14. **System-call failure:** the memory-footprint helper returns `nil` gracefully if `proc_pid_rusage` fails, rather than crashing.
15. **Wrong machine/permissions:** the opt-in test skips cleanly (not a hang or a misleading all-zero result) when `/usr/bin/say` or network is unavailable, for the new 10-voice and new-model variants, not just the original 6-voice Sortformer-only case.

**Complexity:** unchanged order — each candidate is one O(audio length) streaming pass; comparing N candidates over M voice-counts is O(N × M × audio length), same shape as today's 3-candidate loop, just wider. `SpeakerPathReplay`'s path streams audio a buffer at a time (doesn't hold the whole recording in memory); the synthetic `say`-harness still builds its short (tens-of-seconds) clip fully in memory, as today — fine at this scale.
