## North-star fit

**Reuses:** the existing synthetic-voice comparison harness almost entirely — `Packages/CaptionCore/Tests/CaptionCoreTests/SpeakerModelComparisonTests.swift` (opt-in via `CAPTION_SPEAKER_COMPARE=1`, `/usr/bin/say` voice synthesis, FluidAudio's own `DiarizerManager` ground-truth/`DiarizationDER`), `SpeakerModelComparisonReport` (CaptionCore), and `docs/perf/speaker-model-comparison.md` (the doc ADR 0017 already points at for harness details). Memory measurement reuses the exact `task_info(TASK_VM_INFO)` pattern already written once in `Packages/EngineEval/Sources/EngineEvalKit/EngineEvalKit.swift:338-349` (`MemoryFootprint.current()`) rather than inventing a new one — it can't be imported directly (CaptionCoreTests doesn't depend on EngineEval, and that dependency would point the wrong way), so it gets copied verbatim into the test target with a comment citing the original. The driver-script convention (`scripts/engine-eval/m4-speakers.sh`) is reused in spirit (a thin shell wrapper around a deterministic Swift run, writing results into `docs/perf/`), but much simplified: this harness needs no remote audio, rsync, or RTTM alignment — everything is synthesized locally.

**Corrects the ticket's candidate list against the code.** The ticket names "any embedding-and-clustering diarizer in FluidAudio that isn't capped at four speakers." Reading `Packages/CaptionCore/.build/checkouts/FluidAudio/Sources/FluidAudio/Diarizer/`: that's **`DiarizerManager`** (Core/DiarizerManager.swift) — the *streaming* pyannote-3.1-style segmentation+embedding+clustering diarizer, threshold-based speaker assignment with no fixed output-head cap, matching FluidAudio's own CLAUDE.md description ("Online/Streaming"). `OfflineDiarizerManager` is a different, batch-only pyannote path (whole-file `processComplete`, no streaming `addAudio`/`process`) — it can be scored for DER but its time-to-first-label is meaningless (same caveat the Android-engines doc already recorded for sherpa-onnx: "it can't run live as it stands"), so it's an optional bonus row, not a primary candidate. The library also now has **`Nemotron3Diarizer`** — streaming, 8-speaker, not in the ticket's list — which "check what the library offers" invites including. Final candidate set: Sortformer (baseline), LS-EEND/`ami` (ticket-named), `DiarizerManager` (the ticket's "not capped at four" pick), and `Nemotron3Diarizer` (bonus, library-sourced).

**Simplest sufficient approach:** extend the existing harness's shape (parametrize speaker count and model list; add a "call" scenario) rather than building a second parallel harness, and generalize `computeDER`'s two hand-written branches (`sortformerSegments:`/`fluidAudioSegments:`) into one path taking `[SpeakerSegment]`, so a 4th and 5th candidate don't each need their own branch.

**Token/compute cost:** cheap to build (mostly extending ~200 lines of existing, well-tested code); the run itself costs real wall-clock and ~1–2 GB of network (LS-EEND + DiarizerManager + Nemotron3 model downloads) on whichever machine runs `swift test` — unknown whether this pipeline worktree's sandbox has that network access; ADR 0017 hit exactly this wall before. The plan below runs it and reports whatever actually happens, honestly, rather than assume.

**Phone-OS direction:** low — this is a Mac-only measurement (ADR 0028, Mac sold separately); it doesn't move the iPhone/phone-OS vision, but it does keep the shared `Diarizer`-adapter pattern general enough that iOS could reuse it later if a non-4-capped model ever made sense there too.

**User capability:** this ticket is pure measurement + an ADR entry — it doesn't change what the shipped Mac app does today. The user is neither more nor less capable until (if) a later, separately-gated ticket implements a switch.

**Scope boundary (stated plainly, not guessed past):** Owner gates in the playbook require "a mock-up on the ticket and screenshots on the PR" for *any look change*. If the measurement in this run shows a candidate winning outright, I will **not** wire a new bundled model, change `project.yml`/`fetch-diarizer-models.sh`, or touch `Apps/Mac/Sources/CaptionMacModel.swift`'s model URL — that's a look/behavior change (more than 4 visible speaker labels) with no mock-up attached to this ticket. The deliverable this run produces is the harness, the real numbers, and the ADR recording the decision either way; a swap becomes a new, separately-gated follow-up ticket if warranted. This isn't an open question for the owner to pick between options (so it's not a Decisions entry) — it's an existing hard rule already in `CLAUDE.md`/the playbook that this ticket's acceptance criterion #3 ("if switching: screenshots...") can't actually be satisfied in one headless pass without violating.

**Decisions:** none to raise. The ticket's one Decision (`model-delivery`) is already checked `[x] Inside the app`, and the owner's own comment on the issue confirms "Every Decision here is already answered." Nothing else in this ticket requires the owner to pick between options — the candidate-list correction above is implementation judgment, not an open question.

**Known risk from the issue's own history:** two of the three recorded failed attempts were a compile crash near `TranscriptionEngine`/`SortformerConfig` ("error: fatalError") and a code-review rejection. To avoid repeating that: all new adapter code stays contained to the test file (and, where a pure helper is reusable, to new small CaptionCore types) — no edits to `TranscriptionEngine.swift`, `SortformerConfig`, or `LiveDiarizer`'s production code path. No `fatalError`/force-unwraps anywhere in the new code.

## Tests first

The ticket has no "How we'll try to break it" section, so these are derived from the acceptance criteria plus the north star's adversarial checklist, scoped to what's actually new (this ticket is a benchmark/tooling ticket, not a shipped feature — most "misuse" cases are about the harness's own robustness):

1. **Bad/malformed env input:** `CAPTION_SPEAKER_COMPARE_VOICES=garbage` (new env var controlling 4/6/10) falls back to a safe default rather than crashing; same for an out-of-range or negative count.
2. **Huge/unsupported input:** requesting more voices than the machine's `say -v '?'` offers for `en_*` fails loudly with a clear message (not a crash, not silently repeating voices) — a machine with fewer installed voices is a real "wrong environment" case, not hypothetical, given this exact worktree already hit two environment-shaped failures on this ticket.
3. **Each dependency failing independently:** one candidate model's load/download throws (simulate with a fake `URL`/fake adapter, no network needed) — the loop must still run and report the remaining three models, exactly like the existing Sortformer/LS-EEND loop's current `do`/`catch`-per-model behavior, now generalized to 4 candidates.
4. **A person's mistake:** `CAPTION_DIARIZER_MODEL` pointing at a nonexistent path produces a typed error, never `fatalError`/force-unwrap (direct response to this ticket's own recorded compiler-crash failure).
5. **Empty/edge ground truth:** zero-voice and one-voice scenarios for the DER/report pipeline (already partly covered by `SpeakerModelComparisonReportTests`; extend to the new generalized `computeDER`).
6. **Stale global state:** `ModelHub.offlineMode` is a process-global flag Sortformer sets `true` and LS-EEND resets `false`; with a 4th and 5th model added, assert it ends the full run in a known state (not leaking into unrelated tests run in the same process) and that Sortformer's offline guarantee isn't silently broken by a model running after it.
7. **Repeats/determinism:** running one candidate twice on the same synthetic audio gives the same speaker count and DER (no hidden nondeterminism from the clustering-based `DiarizerManager` candidate, whose threshold assignment could in principle be order-sensitive) — matches the existing scoreboard's own "Determinism" measure.
8. **Overlap / malformed audio:** the existing overlap-window construction (summed, clipped) stays covered; add a zero-length / all-silence voice segment case for the "call" scenario's N−1 builder (next item) so an empty far-side never divides-by-zero in DER or memory-per-frame math.
9. **New pure logic, not touching a model:** the "call" scenario's ground-truth builder (N speakers → self excluded → N−1 ground-truth segments) is a pure function; test it directly for N=4,6,10 and for N=1 (a 1-on-1 call has zero "other" speakers to tell apart — must not crash, must report "no comparison needed" rather than divide by zero).
10. **Markdown/report-writer for docs/perf:** the pure function that turns a list of `SpeakerModelComparisonReport` + machine-identity + scenario label into the results table is tested directly for: empty results list, a result with `der == nil`/missing time-to-label (offline model), and duplicate model names (two runs of the same model, e.g. repeat #7) rendering as distinct rows, not overwriting each other.

Tests 1–2, 5–6, 9–10 are pure and run in the default `swift test` suite (no network, no `say`, no model download). Tests 3–4, 7–8 need either a fake/throwing adapter (pure, no network) or the real opt-in run — the ones that only make sense against real models stay gated behind `CAPTION_SPEAKER_COMPARE=1`, same precedent as today.
