# Plan: #214 — Mac: tell apart more than four voices (measure LS-EEND and others)

## North-star fit

**Reuses:** `SpeakerModelComparisonTests.swift` + `SpeakerModelComparisonReport.swift` (ADR 0017's harness: `/usr/bin/say`-synthesized voices, opt-in `CAPTION_SPEAKER_COMPARE=1`, per-candidate try/catch so one model's failure doesn't sink the suite, `DiarizationDER.compute`) is the existing pattern for exactly this measurement and is extended rather than replaced. Memory measurement reuses the pattern in `Packages/EngineEval/Sources/EngineEvalEngines/Speakers.swift:41-47` and `EngineEvalKit.swift:338` (`task_info`/`proc_pid_rusage` process-footprint sampling) — inlined into the test target rather than imported, because the ticket forbids new package dependencies and `CaptionCoreTests` has no existing edge to `EngineEvalKit`. `docs/perf/speaker-model-comparison.md` and ADR 0017 are the existing results/decision docs this ticket updates in place, matching how ADR 0014 has already absorbed three dated follow-up sections rather than spawning new ADRs each time.

**Not reused, and why:** the AMI/CHiME-6 `speaker_eval`/`engine-eval speakers` scoreboard (`docs/perf/speaker-scoreboard*.md`) is real-meeting-recording infrastructure built to resolve half-point DER differences between *compressed builds of the same Sortformer model*. It assumes every candidate is wrapped behind `LiveDiarizer`. LS-EEND and the offline embedding+clustering candidate have different APIs (confirmed by reading `LSEENDDiarizer.swift` and `OfflineDiarizerManager.swift`) and the ticket's own acceptance criterion asks for "numbers for 4, 6 and 10 voices" — a parameter the fixed AMI/CHiME-6 corpora can't give. Pulling in that scoreboard's machinery would be the bigger, not the simpler, sufficient tool here.

**Simplest sufficient approach:** parametrize the existing synthetic harness to 4/6/10 voices, add one more candidate (the uncapped embedding+clustering diarizer), add a process-memory/speed measurement using the same primitive already proven in this codebase, and write the results into the existing perf doc and ADR 0017. No new types beyond what the report already models (one optional field for memory/speed), no new settings UI (ADR 0013 forbids a technical choice in the product regardless of outcome), no network code added to the shipped app (the harness is opt-in, dev/test-only, same as today).

**Tokens:** spent up front reading FluidAudio's actual Diarizer sources (`Nemotron3Diarizer.swift`, `LSEENDDiarizer.swift`, `OfflineDiarizerManager.swift`, `DiarizerTypes.swift`) rather than trusting the issue text's model descriptions, because the issue text is 5 weeks old and the FluidAudio pin has moved since (`0b1f462`, v0.17.5); this is the one place guessing the API would have produced code that doesn't compile. Spent on correctly identifying that `OfflineDiarizerManager.process(audio:)` is a single whole-buffer batch call (confirmed in `OfflineDiarizerManager.swift:130-182`), which matters for how "time-to-first-label" must be reported for that candidate (see Findings note below) — getting this wrong would produce a misleading comparison table that recommends an architecture that can't do live captioning.

**Phone-OS direction:** low direct relevance — this is a measured decision, not a mechanism. It does keep CaptionCore's `Diarizer` abstraction honest across platforms (ADR 0010), which is a precondition for "every device reachable" later.

**More capable or more passive:** more capable — Gil's mother and anyone else using the Mac app in a real multi-person Zoom/Teams call currently loses a 5th+ voice into one of four buckets; a defensible measured decision (switch or stay, documented) replaces a silent limitation. Nothing here reduces the user's own agency; ADR 0013 already rules out exposing this as a user-facing choice either way.

**Which machine:** this worktree's host (the automation Mac, likely the Mini). The ticket calls for memory/CPU "on the MacBook" specifically (Gil's interactive hardware) — that measurement is not available to this headless run; see Decision/caveat below. The synthetic-voice DER/speaker-count/latency numbers do not need Gil's specific MacBook, only *a* Mac, so they are not blocked.

## Feasibility check before committing to scope

Two real blockers from ADR 0017's history are worth re-surfacing rather than re-discovering mid-run:

1. **Network.** LS-EEND (`FluidInference/ls-eend-coreml`, ~89–446 MB per variant) and the offline embedding+clustering candidate's models (`FluidInference/speaker-diarization-coreml`) both auto-download from Hugging Face on first use. This planning session's Bash access is read-only (no `curl`/network probe permitted), so I cannot confirm network reachability from this exact sandbox now. The harness must be written so a blocked download degrades to a clearly-logged `SPEAKER-COMPARE-ERROR` for that one candidate (the existing try/catch already does this) rather than failing the whole run — same honest-reporting posture as ADR 0017, not a new design.
2. **A MacBook with a human.** Real battery/thermal and literal "on the MacBook" memory is Gil's hardware, not this worktree's. This run reports memory/speed measured on whatever Mac executes `swift test` here, labeled plainly as such (consistent with the scoreboard's "measured on the Mac mini M4 only" caveats), not fabricated for a MacBook.

## Tests (written first)

All new/changed tests live in `Packages/CaptionCore/Tests/CaptionCoreTests/SpeakerModelComparisonTests.swift` and `SpeakerModelComparisonReportTests.swift`. The opt-in test stays gated on `CAPTION_SPEAKER_COMPARE=1` (unchanged default-suite behavior, ADR 0007/0014's no-network-by-default constraint).

Ticket's "How we'll try to break it" → this ticket has no such section explicitly, so tests are driven by the acceptance criteria plus the standard misuse list:

1. **4-voice, 6-voice, and 10-voice synthetic meetings** each produce a `SpeakerModelComparisonReport` per candidate per voice count, with `speakersFound ≥ 1` and `0 ≤ der ≤ 1` (extends the existing bound assertions to all three voice counts and three candidates — 9 combinations).
2. **A missing/un-downloadable candidate model does not abort the run.** Simulate by pointing `CAPTION_DIARIZER_MODEL`/the offline-diarizer's model directory at a nonexistent path for one candidate; assert the other candidates still produce reports and the failing one logs `SPEAKER-COMPARE-ERROR` (misuse: "each dependency failing").
3. **`ModelHub.offlineMode` is restored to `true` after the comparison test runs**, regardless of which candidates succeeded or failed (misuse: "stale state" / cross-test pollution — today's test flips it to `false` for LS-EEND and never restores it, a latent bug for every test that runs afterward in the same process and assumes ADR 0007's offline-by-default; fix with `defer`).
4. **Fewer than 10 distinct system voices installed on the run machine skips the 10-voice case with a clear message**, rather than crashing on a `/usr/bin/say` failure for a voice that doesn't exist (misuse: "a person's/machine's mistake" — not every Mac has the same voice set installed).
5. **An all-silence / empty input** to each candidate returns `speakersFound == 0` and `der` well-defined (not NaN/crash) — the current `computeDER` already returns `1.0` for empty hypothesis or ground truth; add an explicit test pinning this for the new candidate's conversion path too (misuse: "empty input").
6. **Overlap window is preserved for 6 and 10 voices**, not just the original 6-voice script (misuse coverage carried over, generalized).
7. **`SpeakerModelComparisonReport` gains an optional memory/speed field** (report test: constructing with and without it, `summaryLine()` still reads sensibly either way) — extends `SpeakerModelComparisonReportTests.swift` the same way `timeToFirstLabel` is already optional.
8. **Two back-to-back runs of the same candidate on the same audio in one process don't leak state** (misuse: "repeats" — relevant because `LiveDiarizer`/`SortformerDiarizer` carry internal FIFO/cache state; assert a fresh `LiveDiarizer`/`LSEENDDiarizer`/`OfflineDiarizerManager` instance per run, which the current code already does per-candidate, so this is a regression guard, not new behavior).
9. **Concurrency:** the comparison test itself stays single-threaded/sequential per candidate (no new concurrency introduced), but add a guard that `LiveDiarizer.feed` ordering assumptions (serial queue) aren't violated when chunk sizes change for the 10-voice case's longer audio (misuse: "wrong order").

## Findings expected to land in the write-up (not assumed — stated as what the harness will determine)

- Candidate table columns: speakers found, DER, time-to-first-label (flagged N/A-as-batch for the offline candidate per the Decision above), model size/license (already known: Sortformer 241 MB/NVIDIA Open Model License; LS-EEND/ami ~89–446 MB/MIT; offline candidate's size/license to be read from `OfflineDiarizerModels`/FluidAudio's own docs once its model is fetched), and process memory footprint on this run's host.
- Ground truth audio excludes a "you" voice for the call scenario, matching how the Mac app's `.call`/`.facetime` listen modes (`CaptionMacModel.swift`) only ever capture the far side via `ProcessTapAudioSource(target: .allSystemAudio)` — the user's own mic isn't in that stream at all, so the synthetic test's N voices should represent *other participants only*, not N including the user. This was the ticket's "two-stream split (#172)" reference; `.both` mode (mic + call mixed via `MixedAudioSource`, confirmed by reading `MixedAudioSource.swift`) is a different, already-existing scenario and is out of scope for this ticket's "Zoom/Teams meeting" framing.
