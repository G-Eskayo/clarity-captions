## North-star fit

- **Reuses before adding anything new:** `TailCommitter`/`ParakeetEmitter` (`Packages/CaptionCore/Sources/CaptionCore/TailCommitter.swift`, `ParakeetBackend.swift`) for commit semantics — unchanged logic, one parameter tuned; `SessionLog`/`replay.py`'s `score_arm`/`paired_gap`/`by_fallback`/`language_gate` (`Packages/SystemReplay/Sources/SystemReplayKit/SessionLog.swift`, `scripts/system-replay/replay.py`) as the one measurement harness, extended rather than duplicated; `edacc_eval.wer.align_counts`/`normalize` for alignment, instead of a second aligner; `CaptionStream.defaultPauseSeconds` (1.2 s, `CaptionStream.swift:57`) mirrored as the line-break rule rather than invented; the already-existing opt-in, real-model harness `ParakeetIntegrationTests.swift` (`say` → `TranscriptionEngine.startReplaying`, `editDistance`, `CAPTION_PARAKEET=1`) as the only available real-model evidence source in this sandbox, instead of writing a new one; `CaptionEngineRouting.parakeetLanguages` (`EngineFallbackPolicy.swift:38`) as the source of truth for which locales would even reach the language hint; `onDecode`'s existing callback pattern (`ParakeetBackend.swift:109`, `TranscriptionEngine.swift:213`) as the template for the one new callback.
- **Why it's the simplest sufficient approach:** two of the ticket's three boundary types (committed-tail boundary, line break) are already fully reconstructable from `SessionLog.Update.isFinal/start/end/speaker`, which exists today — no new field needed for them. Only the third ("a decode-window seam") needs new instrumentation, because it happens at every hop, not just at a commit. So the Swift surface is one new field (`SessionLog.decodeWindows: [Double]`) plus one new callback, not a second logging system.
- **Where it spends vs. saves tokens:** spends on a small, bounded config change (one number) plus pure, fast, already-styled tests; saves on every future accuracy ticket on this path, which reuses the same per-boundary breakdown instead of re-deriving one.
- **More capable, not more passive:** yes for the primary user — closing (or, honestly, narrowing) the 3.4-point gap between what Parakeet can do and what she actually reads is exactly north star 3's "quality is the product" test.
- **A north star argues against part of this:** "Verified, not assumed" (guiding principle) is why I will not claim the ticket's WER-CI-overlap criterion is met — see "What's genuinely blocked" below. It does not argue against attempting a real, tested fix; see "What I found" for why I think the last two attempts read it that way and that reading is why they failed review.

## The actual fix candidate, and why

`TailCommitter.Config.leftContext = 1.0` (`TailCommitter.swift:35`) controls how much audio before `commitPoint` is kept and re-decoded every hop; everything before `windowStart = commitPoint - leftContext` is permanently trimmed (`ParakeetBackend.swift:204`, `window.trim(before: keep)`) and never seen again. For a continuing sentence — the "run-on sentence forced to commit at 12 s" and "fast speaker turns" cases the ticket names — the word right after a commit point gets only 1.0 s of real preceding speech to disambiguate against, well under what a 15 s-capable encoder (`maxWindow = 14.5`, "under the encoder's 15 s input") is built for. There's large headroom to raise it: in steady state the window is `(audioEnd − commitPoint) + leftContext`, nowhere near the 14.5 s cap even at `leftContext = 2.5`–`3.0`. This is testable without the model: `TailCommitterTests.swift`'s own 10,000-session adversarial fuzz test (`testRandomSessionsCommitExactlyTheTrueWordsInOrder`) already proves the agreement algorithm itself never doubles or drops words under timing jitter, independent of `leftContext` — so this is a context-size tuning change, not a logic change, and carries no regression risk to correctness already proven by that fuzz test.

I will **not** claim this closes the ticket's WER-CI-overlap criterion — that needs the real corpus run. I will land it as the evidence-reasoned primary candidate, backed by: (a) pure `TailCommitter`/`AdaptiveHop` unit tests proving commit mechanics are unchanged and window-size bounds still hold; (b) a small, opt-in, real-model check (below) that is the most real evidence obtainable inside this sandbox.

## Design

1. **`ParakeetBackend`**: add `onWindow: (@Sendable (Double) -> Void)?`, fired with `shot.start` — but, fixing a bug I found in both prior attempts' own draft of this (they fired it even when `decode()` returned `nil`, i.e., a failed transcribe) — **only when `decode(...)` actually returned a result** (use `if let words = await decode(...)` as the gate in the `settleRequested` branch too, not `?? []`), never in `finish()` (nothing follows a terminal flush, so it isn't a seam).
2. **`ParakeetBackend.language(for locale:) -> Language?`**, a pure helper (maps the 6 `CaptionEngineRouting.parakeetLanguages` codes to FluidAudio's `Language`, `nil` otherwise — never traps on a malformed identifier), threaded into `init(modelURL:locale:)` (default `en-US`, so the two test-only call sites in `FaceToFaceSpikeTests.swift`/`BundledModelsTests.swift` keep compiling unchanged) and passed as `language:` into both `manager.transcribe(...)` call sites in `decode(...)`. `TranscriptionEngine` threads its own `locale` at `makeBackend()` (`TranscriptionEngine.swift:212`) and the face-to-face closure's own `locale` parameter (`TranscriptionEngine.swift:176`); the static `warmUp(parakeetModelURL:)` (`:662`) keeps the default — it never decodes real content. Documented as a cross-script guard only (update the "Parakeet takes no language setting" line in `EngineFallbackPolicy.swift:33`'s comment, since that's no longer quite true, and `docs/design/parakeet-engine-switch.md`).
3. **`TailCommitter.Config.leftContext`**: 1.0 → 2.5 (Decision `leftcontext-value` below picks the exact number).
4. **`SessionLog.decodeWindows: [Double]`** (new field, defaults to `[]`), wired from `TranscriptionEngine.onDecodeWindow` into `main.swift`'s `replay()`, next to the existing `watchFallbacks` wiring.
5. **`scripts/system-replay/replay.py`**: new pure functions `update_spans`, `boundary_positions`, `boundary_errors`, mirroring `language_gate`'s style — classify each error from `align_counts`'s alignment by nearness (configurable word margin) to a seam (`decodeWindows`), a commit boundary (every final `Update`'s own start), or a line break (pause ≥ 1.2 s or speaker change between consecutive finals, mirroring `CaptionStream.swift:139`), tagging non-exclusively plus an explicit `"elsewhere"` bucket, scoped to sessions that stayed on Parakeet (reuse `left_parakeet`/`by_fallback`'s stratification). Wired into `score()`/`markdown()` as a new table — this **is** the "regression check added to how builds are scored" (criterion 4), fully unit-testable with synthetic `SessionLog`-shaped dicts, no real audio needed.
6. **Real-but-small evidence, best-effort**: extend `ParakeetIntegrationTests.swift` (same `say`-synthesized-audio, `CAPTION_PARAKEET=1`, `editDistance` house style) with cases that directly exercise the ticket's "How we'll try to break it" list: a lone one-word utterance after a pause; a long run-on sentence with no pauses past 12 s; two injected pauses placed to land a commit/line-break at a known word. ## Decisions

<!-- marvin:decisions -->
### leftcontext-value: `TailCommitter.Config.leftContext` (1.0 s today) — how much to raise it
- [ ] 2.0 s (smallest change that still roughly doubles context; least decode-cost increase)
- [ ] 2.5 s (recommended — meaningful increase, still leaves >10 s of headroom under `maxWindow`'s 14.5 s cap)
- [ ] 3.0 s (largest tested increase; more decode cost per hop, `AdaptiveHop` should absorb it but increases average decode-window size)

### boundary-margin: words of distance ("N") that count as "near" a boundary in the per-boundary classifier
- [ ] 3, same for all three boundary types (matches `TailCommitter.alignWords`, simplest)
- [ ] 1 for line breaks (the ticket's own example is errors *at* the break), 3 for seams/commit boundaries

## Tests first (red before green)

1. **`TailCommitterTests.swift` (extend)**: `windowStart(audioEnd:)` with the new `leftContext` still never goes negative and never exceeds `maxWindow`'s bound (extend `testWindowStartKeepsLeftContextAndNeverGoesNegative`); a forced-12 s-commit scenario (extend `testForceCommitAtTwelveSecondsUncommitted`) shows the *next* window after the forced commit has `leftContext` s of real preceding speech, not just 1.0 s — the concrete claim this fix makes; the existing 10,000-session fuzz test re-run unchanged (not duplicated — it already runs with whatever `Config()` default is in force, so it becomes the regression guard for the new default, no edits needed beyond config's own default).
2. **`ParakeetBackendLanguageTests.swift` (new, pure)**: `ParakeetBackend.language(for:)` maps all 6 `CaptionEngineRouting.parakeetLanguages` codes correctly; returns `nil` for Hebrew, Japanese, Chinese, a malformed/empty `Locale(identifier: "")`, and any code outside the 6 — never traps.
3. **`ParakeetBackend` onWindow placement (new, in existing `ParakeetMappingTests.swift` or a small new file)**: a seam fires only on a successful decode, never when `decode()` returns `nil` (a dependency failure) and never from `finish()`'s terminal flush — this is the concrete fix to the bug I found in both prior drafts.
4. **`TranscriptionEngine` wiring (extend `TranscriptionEngineBackendTests` if it exists, else new)**: `makeBackend()`'s `.parakeet` case and the face-to-face `.parakeet` closure case both construct `ParakeetBackend` with the engine's own in-scope `locale`, not a hardcoded default — asserted through the real construction path, not by calling the pure helper twice in isolation (the weak-test pattern I found in the second prior attempt's draft).
5. **`SessionLogTests.swift` (extend)**: `decodeWindows` defaults to `[]`, round-trips through JSON non-empty and empty, `record(_:)` behavior unaffected.
6. **`scripts/system-replay/tests/test_replay.py` (new section)**:
   - `update_spans`: three final updates with known texts give the right contiguous index ranges; a session whose per-update and whole-string normalization disagree is reported as excluded, not misattributed (refuse rather than guess, matching `conversation_of`'s style).
   - `boundary_positions`: a pause ≥ 1.2 s marks a line boundary, a speaker change with no pause also marks one, a pause just under 1.2 s does not; a `decodeWindows` timestamp between two spans attaches to the next one, never a negative or past-the-end index; an **empty `decodeWindows` list** (a session that ran on Apple, not Parakeet) yields zero seam boundaries, not a crash.
   - `boundary_errors`: a substitution right after a commit tagged `"commit"`; one far from everything tagged `"elsewhere"`; one near both a line break and a seam gets both tags (non-exclusive); a deletion attributed to its nearest surviving neighbour, not dropped; **misuse**: an empty hypothesis, an empty reference, a session log with zero final updates, a session log whose `error` field is set (must raise, matching `session_text`'s existing behavior), and a session that left Parakeet mid-way (excluded entirely, matching `by_fallback`'s stratification) — all handled without crashing.
7. **How we'll try to break it, explicitly from the ticket's list:**
   - *A one-word utterance alone in a window, must come out in the caption language* → test 2 (pure) proves the hint is correctly wired for the case it *can* help (cross-script); the plan states plainly it does not fix the cited same-script "olha jestli" example, and the opt-in real-model test (design §6) is the only way to check the lone-word case against the real model, gated on model availability.
   - *A word split across a seam, repeated word across it ("the the")* → already covered by `testARepeatedWordAcrossTheCommitPointIsNeitherDoubledNorSwallowed` and the fuzz test; this ticket only adds the ability to *locate* such an error against a seam after the fact (test 6's `boundary_errors`), so no duplicate test.
   - *A long run-on sentence forced to commit at 12 s* → test 1's extended `testForceCommitAtTwelveSecondsUncommitted`, plus test 6's `boundary_positions` with a `decodeWindows` timestamp strictly between two spans.
   - *Fast speaker turns landing a line break and a seam on the same word* → test 6's non-exclusive multi-tag case.
   - *Fixing accuracy by waiting longer, caught by the lag criterion* → the raised `leftContext` increases decode-window size, not hop frequency; `AdaptiveHopTests.swift`'s existing suite is unaffected (no change to `AdaptiveHop` itself), and I'll say plainly that real lag impact needs the same blocked corpus run as criterion 3.
